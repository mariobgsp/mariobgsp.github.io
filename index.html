routre

One static Go binary that cuts AI token bills and fails over providers for any CLI.

  • Go
  • LLM gateway
  • OpenAI-compatible
  • token compression
  • failover
  • single binary
94.8%RTK tool-token reduction
93.3%Worst per-payload reduction
12.6 MiBIdle RSS

routre is a small local gateway that sits between your AI apps and AI providers on your own machine. Point a coding agent at http://127.0.0.1:20128 once and it keeps working while routre shrinks repetitive tool output before it is billed, replays identical requests from a cache, and switches to the next provider if one is busy or down.

Tech stack

Go, standard library only
One static binary (10.9 MiB, ~12.6 MiB idle) with no Node, Python, Postgres or Redis; the proxy is net/http, so no framework sits between the reader and the request path.
HTTP + SSE dialects
internal/proxy/dialect/ is a cross-kind SSE state machine (OpenAI to Anthropic to Gemini), which is what lets one address serve every OpenAI/Anthropic-compatible CLI.
RTK compression
11 heuristic tool_result filters (git diff and log, grep, tree/ls/find dedup, build output, smart truncate) that never grow a payload and fail open; the shipped level measures 94.8% aggregate tool-token reduction.
LRU response cache
Exact-match on the SHA-256 of the canonical body after RTK; streaming and non-streaming entries share a key space but never cross, and an on-disk snapshot keeps the cache warm across restarts.
Local config + loopback dashboard
routre setup writes config.json and routre.env (0600), and the loopback-only /ui edits keys and routing without hand-editing JSON.

Code structure

  • main.go plus one file per command - setup.go, start.go, stop.go, list.go, models.go, bench.go, update.go; bench.go is the gate that fails on any RTK regression below the target.
  • internal/proxy/ - the pipeline with runner.go for retry and failover; internal/proxy/dialect/ holds the cross-kind SSE state machine.
  • internal/rtk/ - the 11 heuristic tool_result filters, each bounded by a 512 KiB scan window and a 150 ms budget.
  • internal/cache/ - the exact-match LRU keyed on the SHA-256 of the canonical post-RTK body, with its on-disk snapshot for warm restarts.
  • internal/router/ - tier walking and per-provider cooldown; internal/usage/ - the ~/.routre/usage.json token and cost ledger.
  • The loopback-only /ui dashboard is served from internal/proxy/, so the gateway and its settings page ship in the same binary.

Architecture

  • Every request walks the same seven steps: detect dialect, RTK compress, cache lookup, tiered route, candidateRunner retry, translate, relay.
  • Compression is bounded and fail-open: no filter may enlarge a payload, and the work stops at the scan window or the time budget rather than delaying the request.
  • Routing prefers the cheapest healthy provider: tiers are walked in config order (subscription, then cheap, then free) and a failure puts that provider on an exponential cooldown from 2s to 5m.
  • Failover is bounded, not open-ended: one transient retry, one auth refresh on 401/403, then the next candidate; timeouts.candidate_seconds defaults to 45s with one bounded 45s extension and a 120s header ceiling.
  • The ledger is derived from the path that bills: internal/usage/ records per-agent tokens and cost, including what RTK and the cache saved.
  • Savings are measured on tool-result tokens only - output tokens are never compressed - so the published percentage is a benchmark instrument, not a billing guarantee.

Why it exists

Agent traffic is repetitive: the same diff, the same grep hits, the same build log are re-sent on every turn and billed again. routre sits on the loopback address between the app and the provider, shrinks that noise before it is billed, and answers identical requests from cache - so a session costs less without the agent changing.

The second motive is availability. Subscription providers get busy or rate-limited mid-task, so the gateway walks provider tiers and fails over instead of failing the request, and keeps a per-agent ledger because nobody could otherwise say what a session actually cost.

02 · TypeScript

arness

Lean local AI coding harness: one binary, CLI + TUI, MCP/LSP, skills, extensions, optimizer.

  • TypeScript
  • CLI + TUI
  • MCP/LSP
  • extensions
  • single binary

arness is a coding agent that runs entirely on your machine as one binary: an interactive TUI and a print mode over the same turn loop, with tools (bash, filesystem, search), skills, an extension API, MCP and LSP capabilities, subagents, memory and a token optimizer.

Tech stack

TypeScript on Node 26
Erasable syntax only, checked with tsc --noEmit; TypeScript is the only devDependency, so the source carries no build-time framework.
bun build --compile
One self-contained executable per platform; install.sh and install.ps1 drop it under the user data directory and link a shim onto PATH.
node --test
The suite runs on the runtime's own test runner with no framework; provider streams are parsed against committed SSE captures, so tests never touch the network.
MCP + LSP
src/capabilities/ attaches MCP servers and a language server to the session, so context comes from real tools rather than from the loop guessing.
JSONL event log + savings ledger
One event log per session under the state directory makes /fork and /switch cheap; optimizer.jsonl keeps one savings row per provider call.

Code structure

  • src/main.ts - entrypoint and mode selection: interactive TUI, or -p for one turn, print and exit.
  • src/core/ - config, events and session, the turn loop, system prompt and skills, token accounting and rendering (config.ts, events.ts, session.ts, loop.ts, system-prompt.ts, skills.ts, tokens.ts, render.ts, commands.ts, context.ts).
  • src/tools/ - the bash, filesystem and search tools plus the registry; src/ext/ - the extension loader, hooks, host and types.
  • src/capabilities/ - MCP, LSP, subagents, memory, review, search and todo guards.
  • src/optimizer/ - prefix order, compression, clamp, breakpoints and prune, with report.ts and rtk.ts; src/providers/openai.ts is the provider adapter.
  • src/tui/ - input, theme and the terminal UI; test/ - node --test suites with committed SSE fixtures; scripts/check-names.mjs guards against foreign harness references.

Architecture

  • One loop, two front ends: the TUI and print mode drive the same turn loop, so a scripted run and an interactive session take an identical path through tools, capability hooks and the optimizer.
  • The optimizer runs before the request: it rewrites the outgoing payload and appends a savings row per provider call, which is what makes the ledger auditable.
  • Sessions are files: every event is appended to sessions/<cwd-slug>/<iso>_<id>.jsonl, so forking, switching and inspecting a session need no database.
  • Extensions hook the loop: src/ext/ exposes lifecycle hooks, and a tool_call hook can veto a call before it runs, so policy can be added without editing core.
  • Capabilities are attached, not baked in: MCP servers, a language server, subagents and memory are registered onto the session, which keeps the loop small and the surface testable.
  • Boundaries are stated rather than implied: the bash tool is unrestricted code execution with no isolation layer, and the extension hook is the intended place to add policy.

Why it exists

Most harnesses are a hosted runtime with a CLI attached. arness is the opposite: one local binary you own, where the turn loop, the tools, the provider adapter and the optimizer all live in a single TypeScript source tree, and nothing leaves the machine except the provider call you configured.

The optimizer exists because agent sessions are mostly repetition. Prefix ordering, compression, clamping, breakpoints and pruning are applied before the request, and every saving is appended to a ledger - so the number can be checked instead of claimed.

t-notes is a single-user notes app and a kanban board in one, with all data kept in your own browser - nothing is sent to a server, and there is no account or sync service.

Tech stack

Vanilla HTML, CSS and JavaScript
web/index.html, styles.css and app.js are the entire UI - no framework, no bundler, no npm install; content-visibility: auto keeps long lists cheap and the three themes are plain CSS.
localStorage
The only datastore: all state lives under the key t-notes-v1 and is written on every mutation, so there is no API client and no server-side session.
Go with //go:embed
main.go embeds web/ and serves it from a local net/http server, opens the default browser, and self-installs or uninstalls from the same binary.
Tauri v2 + Rust
The desktop shell: one Rust command (match_notes) for batch substring search with a JS fallback, and an NSIS installer with a launch-on-login plugin.
Playwright
e2e/t-notes.spec.js (15 tests) runs against system Chromium with a mocked AI endpoint; build-windows.sh cross-compiles the Windows exe and setup exe from Linux.

Code structure

  • web/ - the entire front end: index.html, styles.css, app.js and logo.svg, with const K = t-notes-v1 at the top of app.js as the storage key for all state.
  • main.go - the Go host: //go:embed web/, the local net/http server, browser launch, and the setup/--install and --uninstall paths.
  • src-tauri/ - the desktop shell: src/main.rs exposes match_notes, and tauri.conf.json sets frontendDist to ../web and bundles the NSIS installer with tauri-plugin-autostart.
  • e2e/t-notes.spec.js - the Playwright suite, run against system Chromium with a mocked AI endpoint.
  • build-windows.sh + go.mod - cross-compile the Windows exe and setup exe from Linux.

Architecture

  • One store, two views: notes pinned to a board list render as cards, so the board and the notes view are the same objects and an edit in either is the same write.
  • Two host paths share one front end: the Go exe acts as a browser launcher (with an /api/startup fallback for the power toggle) and the Tauri app opens its own window and installer.
  • State is local-first by construction: no sync layer, no account and no multi-device story - the only optional network call is the bring-your-own-key AI request.
  • The AI assistant keeps the key in the browser and never exports it; summaries, checklists, rewrites and ideas all run against the URL and key the user supplies.
  • Long lists stay cheap by capping what is rendered (a 50-item window) and letting content-visibility skip off-screen work.

Why it exists

t-notes is the answer to using a board and a notes app for things that should never leave the laptop: no account, no sync service, no build step and no framework. All data stays in browser localStorage, and the board and the notes are one system - a note pinned to a list renders as a card in both views.

It also exists to show how small that can be: the entire UI is three static files, the Windows build is a 9.7 MiB Go exe that embeds them, and the Tauri shell adds one Rust command for large-corpus search.

04 · Go

Payment System

Idempotent Go payment lifecycle: order, charge, HMAC callbacks, outbox, refunds.

  • Go
  • PostgreSQL
  • Redis
  • Next.js
  • Docker Compose

A working payment lifecycle built end to end: a customer signs in, picks a product, places an order, charges it, and refunds it. Every state change runs through one TransactionLifecycle module that pairs a PostgreSQL transaction with an outbox row and an idempotency key, so retries and duplicate clicks cannot double-charge.

Tech stack

Go
The whole backend is one binary. Lifecycle, store and jobs are plain Go over database/sql with no ORM, so the transaction boundary and the idempotency insert stay visible in one function.
PostgreSQL
System of record for the transaction and store schemas: one SQL transaction writes the state change, the outbox row and the idempotency key, which is what makes retries safe.
Redis
Short-lived charge state for the partner stub (ms-paymentagr), so the fake provider can behave like one without a database of its own.
Next.js 16 + TypeScript + Tailwind
The portal - login, catalog, checkout, status, refunds. Its server-side client (frontend/src/lib/gateway.ts) calls the monolith, so browser code never holds a partner key.
Docker Compose
Five containers (postgres, redis, ms-paymentagr, monolith, frontend) from one command; pg-init-scripts seed schemas, demo users and products, so the lifecycle is runnable with no cloud account.

Code structure

  • monolith/lifecycle/ - the deep module: lifecycle.go holds the state chart (CREATED to READY to SUCCESS/FAILED/REFUND) plus idempotency, and pricing.go holds the discount math.
  • monolith/cmd/ - wiring and the endpoint table: routes.go, handlers.go for the new API, legacy.go for the ms-* compatible paths, http.go for envelopes plus partner and outbox transport.
  • monolith/store/ - the persistence seam: store.go types with pg.go for production and memory.go as the dev/test fake, over the transaction + store schemas.
  • monolith/jobs/, monolith/invoice/, monolith/invoiceworker/ - the background half: the outbox poller, the sweeper and the invoice worker that writes receipt files.
  • ms-paymentagr/ - the partner stub (Go/Gin + Redis): usecase/ drives charge, refund, the CheckoutUrl page and HMAC-SHA256 callbacks behind the api-key header.
  • frontend/ - the Next.js portal; frontend/src/lib/gateway.ts is the only place that talks to the monolith.

Architecture

  • State only changes through the lifecycle module: the state change, the outbox row and the idempotency key are written in one PostgreSQL transaction, so a repeat of the same Idempotency-Key returns the original result instead of charging twice.
  • Callbacks are verified before they are trusted: HMAC-SHA256 over the body with a 300s replay window; a forged signature is rejected with 401 and never reaches the lifecycle.
  • Asynchronous work is a table, not a queue client: outbox.go polls every 5s, routes ms-notify-payment rows to the invoice worker and keeps servicelogs queryable, retries with 3x backoff and terminates poison messages in a dlq.* row.
  • The sweeper keeps stale state honest: READY transactions older than 5m move to FAILED, and servicelogs are purged past LOG_RETENTION_DAYS.
  • The invoice worker writes INVOICE_DIR/invoice_<tx>.json and sanitizes the transaction id against path traversal before it touches the filesystem.
  • The README publishes no benchmark numbers: splitting the monolith is explicitly deferred until a load measurement justifies it, which is why this repo shows a lifecycle rather than a throughput claim.

Why it exists

Payment retries are where systems go wrong: a customer double-clicks, a partner callback arrives twice, a worker dies mid-flight. This repo keeps those paths in one place - a single TransactionLifecycle module that pairs the PostgreSQL transaction, the outbox row and the idempotency key - so there is exactly one way a payment changes state.

It was written as a reference implementation rather than a product: the unglamorous half of payments as code you can start with docker compose, break on purpose and read. HMAC-verified callbacks with a replay window, an outbox poller that ends poison messages in a DLQ, and a sweeper that keeps stale state honest.

The Gateway

Next.js BFF over a Go gateway: register upstream APIs, forward calls server-side.

  • Next.js 15
  • React 19
  • TypeScript
  • chi + pgx
  • PostgreSQL
  • Kubernetes
5 fails / 10 minConfig: login throttle
2 to 10Config: HPA replica range
30s (5s dial)Config: upstream timeout

It is a self-hosted API management console: you register an upstream API by giving it an identifier, host, path, method, and the headers or parameters it may pass through, then the gateway forwards those calls for you.

Tech stack

Next.js 15 + React 19 + TypeScript
BFF and console in one app: route handlers and server-side lib code mean the JWT never has to leave the server, and the console is plain app-router pages.
Go (chi + pgx)
The gateway itself: a small router, one typed store file per entity over pgx, and forwarders with explicit dial and client timeouts.
PostgreSQL
Users, store accounts, registered APIs, and the system_properties row that holds the signing secret - read per request rather than cached in the process.
JWT + httpOnly cookie
Auth across the seam: login issues a JWT, the BFF keeps it in a SameSite=Lax httpOnly cookie, and a Bearer middleware in Go guards everything except /health and login.
Kubernetes
The Go service ships with a Deployment (2 replicas, /health probes, 32Mi request / 64Mi limit) and an HPA that scales 2 to 10 pods on CPU 60% and memory 70%.

Code structure

  • frontend/src/app/gw/[...path]/route.ts - the catch-all BFF route; frontend/src/lib/gwRoutes.ts is the declarative route table and frontend/src/lib/bffGateway.ts owns session-to-401 mapping, the 20s AbortController, sanitization and envelope translation.
  • frontend/src/lib/session.ts and frontend/src/middleware.ts - the httpOnly cookie session and the guard over /home, /api/* and /store/*.
  • gateway-go/internal/handler/ - chi routes plus the Bearer-token middleware; only /health and /gateway/user/login stay public.
  • gateway-go/internal/store/ - one file per entity (user, account, api, postgres.go) over pgx.
  • gateway-go/internal/service/ - forward.go (typed ForwardRequest) and upstream.go (persisted header allowlist, single query encode, 5s dial / 30s client timeout).
  • k8s/gateway-go/ - deployment.yaml and hpa.yaml.

Architecture

  • All backend calls are server-side: the browser only ever talks to the Next.js BFF, which attaches the JWT from the httpOnly cookie and translates upstream failures into NextResponse envelopes.
  • The route table is data, not code: gwRoutes.ts declares which gateway paths exist, so adding an upstream surface is an edit in one file - and the current table accepts only GET and POST.
  • Auth is two-layered: the BFF owns the session cookie, and the Go service re-checks the Bearer token on everything under /api/gateway and /api/store before a handler runs.
  • Forwarding is allowlisted: upstream.go applies the persisted header and parameter allowlist, encodes the query once, and bounds the call with a 5s dial and 30s client timeout.
  • Scale-out is declared rather than assumed: the HPA runs 2 to 10 pods, while login throttling is per-username and in memory, so it resets on restart and does not aggregate across replicas.
  • The Kubernetes manifests cover gateway-go only; the frontend and PostgreSQL run outside the cluster, and the repo publishes no load-test numbers.

Why it exists

Every internal tool ends up with its own copy of the same upstream credentials. This repo is the counter-example: an upstream API is registered once - identifier, host, path, method, allowed headers and parameters - and every client calls the gateway instead of the upstream.

It is also a deliberate exercise in keeping a token out of the browser. Browser to Next.js BFF to Go service, with the JWT in an httpOnly cookie and the signing secret read per request from system_properties, so no JWT ever reaches browser JavaScript or localStorage.

Trading Suite

Self-hosted IDX market desk: FastAPI over a SQLite WAL cache, five UI routes.

  • Python
  • FastAPI
  • Next.js
  • TypeScript
  • SQLite
39 passedBackend test suite
900+ tickersIDX universe in config
22 apps to 5UI routes after lean pass

A self-hosted desk for the Indonesian stock market (IDX). It pulls quotes, history, foreign flow and broker activity from public feeds, caches them, and turns them into five screens: an overview, a charting page with foreign-flow bars, a streaming screener, a per-ticker profiler, and calculators.

Tech stack

Python + FastAPI
The backend: one router per domain (market, screener, validator, intel, analysis, regime, backtest, portfolio, summary, alerts, sentiment) with the analysis kept one level up in service modules.
SQLite in WAL mode
The cache seam: per-feed TTLs with stale-while-revalidate in backend/data/cache.db, so a screen refresh does not hammer the public feeds.
Server-Sent Events
The screener streams results from GET /api/screener/scan/stream and the client mirrors the same cache policy in src/lib/cache.ts (memory + sessionStorage).
Next.js 16 + React + TypeScript
The five UI routes (overview, markets, screener, profiler, calculators) after a lean pass from 22 app routes; the nav is generated from one source in src/lib/apps.ts.
curl_cffi + yfinance
The data path: an IDX summary endpoint and .JK history - cached copies of third-party feeds, not an exchange-grade tick store, and the repo says so.

Code structure

  • backend/app/main.py - wires the routers; backend/app/routers/ holds one router per domain and the services live one level up in backend/app/*.py.
  • backend/app/screener.py, idx.py, cache.py, db.py - the scan path: the suspended-ticker filter runs before the ThreadPool fan-out, then results stream over SSE from the SQLite WAL cache.
  • backend/app/validator.py - BandarmologyAnalyzer (phase, intent radar, flow metrics) behind GET /api/validator/{ticker} and inside the profiler page.
  • backend/app/_fifo.py + portfolio.py - the FIFO P/L engine and its JSON load/save; backend/app/backtest.py + routers/analysis.py - the pattern backtests. Both are API-only: next.config.ts redirects /portfolio and /backtest to /profiler.
  • frontend src/app/{overview,markets,screener,profiler,calculators} with src/lib/apps.ts as the single nav source, and backend/data/cache.db as the only datastore.

Architecture

  • Caching is the seam that makes it cheap: per-feed TTLs in a SQLite WAL file with stale-while-revalidate and _spawn_refresh dedupe, mirrored in the browser by src/lib/cache.ts.
  • A scan is filtered before it is fetched: the suspended-ticker filter runs in idx.py before the ThreadPool fans out, so excluded names never reach a feed.
  • The API is the product surface: routers stay thin and the analysis lives in service modules, so the profiler page, the validator endpoint and the backtest endpoint all read the same engine.
  • Nothing is stored in a company cloud: quotes live in backend/data/cache.db and the only outbound calls are to the public data sources.
  • AI summaries are no longer a feature: backend/app/ai.py is an explicit no-op stub that returns None and nothing imports it, so every caller falls back to deterministic text.

Why it exists

This repo exists to answer one question once a session: which Indonesian stocks should be bought at the next open, and why. It is a self-hosted desk - your own FastAPI backend, your own cached copy of the market data - instead of another market-data subscription.

The strongest feature is bandarmology, Indonesian broker-flow analysis: phase, intent radar and flow metrics computed from broker activity, with a FIFO portfolio engine and a backtest surface behind the same API, so a number on screen can be traced back to the code that produced it.

It screens roughly 900 IDX/IHSG tickers each morning against the Minervini Trend Template (8 checks) plus a VCP contraction score, then plans the entry zone, stop and targets for the ones that qualify.

Tech stack

Python 3.11+ and pandas
The whole tool is one CLI (trading_cli/cli.py); indicators and scan math are pandas over daily bars - no server, no API keys, no database to run.
yfinance + SQLite
The data path: a throttled 4-thread fetch with rate-limit backoff over a 12h-TTL WAL cache in the XDG cache directory, with stale-while-revalidate.
Minervini Trend Template + VCP
The screen itself: 8 trend checks plus a volatility-contraction score, with relative strength measured against ^JKSE before any candidate is planned.
Walk-forward validation
Rolling train-252 / step-60 windows: a threshold is kept only when it survives unseen data, which is why the README reports roughly 50% pooled win rate instead of a 70% sleeve.
Expectancy + Wilson interval
Ranking is by expectancy p*avgWin + (1-p)*avgLoss and a 95% Wilson bound, not raw win rate, so a high win rate with 0.5R losers cannot top the leaderboard.

Code structure

  • trading_cli/cli.py - the whole surface (the trading-cli script in pyproject.toml): flags, scan, expectancy ranking, qualifiers split from near_miss, JSON out.
  • trading_cli/scan.py, minervini.py, data.py, cache.py - universe fetch and throttling, trend template, VCP score and relative strength over the SQLite cache.
  • trading_cli/backtest.py + regime.py - the 18-entry STRATS table, next-open fills with fees and slippage, and the regime tags each trade carries.
  • trading_cli/validate.py + tune.py - walk-forward out-of-sample replay and the VCP threshold grid under the same gate.
  • trading_cli/entry.py + ml_filter.py - buy zone, tightest stop and T1/T2/T3 targets, plus the pooled-n and leakage guards that keep future ML work honest.

Architecture

  • One pass produces the answer: scan the universe, gate on regime (ADTV, ATR14, IHSG stage, CMF), rank survivors by expectancy, then split them into qualifiers and near_miss.
  • Every pick carries its evidence: the strategies that backtested it, the pooled win rate with a Wilson bound, and the regime tag at entry.
  • Thresholds are earned rather than chosen: validate.py replays strategies on rolling windows and tune.py grids VCP thresholds under the same out-of-sample gate.
  • The entry plan is derived from the pivot: the 20-day high becomes the buy zone, and the tightest of the 20-day low, close minus 2 ATR or -8% becomes the stop.
  • Data is daily and best-effort: yfinance with throttle and backoff, so coverage is only as good as that feed - reported in the README rather than hidden.

Why it exists

Most screeners answer with a list and no accounting for whether the list makes money. This one answers with a plan and an honest no-trade: roughly 900 IDX tickers screened each morning, then every qualifying pick backtested against 18 strategies with real fees and slippage, tagged with the market regime at entry and re-checked walk-forward out-of-sample.

The output is machine-readable JSON on purpose - picks, near_miss, leaderboard, regime_pooled, wf_regime - so a swing trader or an agent can run it before the open and sit out when the evidence is thin instead of forcing a recommendation.
