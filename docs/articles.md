# The articles section: automatic sync, and what Substack-grade rendering would cost

The design record for `tools/build-articles.py`, `.github/workflows/articles-sync.yml`
and the article pages. Written for the next contributor, human or agent, who has to
change one of them.

## Problem

Every string on `/articles/` is generated from the articles repository, but the
*set* of articles and several facts about it were maintained by hand in five
places, each free to drift from the others:

| Hand-maintained | Consequence when a sixth article is pushed |
| --- | --- |
| `SLUGS` in the generator | The article exists on GitHub and on no page of the site. |
| `sitemap.xml` | The new URL is never submitted. |
| `assets/articles/og-<slug>.png`, referenced unconditionally | The new page advertises a social card that 404s. |
| `README.md` "The five" in the articles repo | The source document contradicts the site. |
| `index.html` prose, count and list outside the generated region | "Five articles, one habit" stays on the served page forever. |

Nothing ever removed a page either: only images were pruned, so a renamed or
deleted article kept serving a 200 at its old URL — and `--check` compared only the
pages it generated, so the orphan never showed up as drift.

Separately, `Renderer.blocks()` is a ~120-line state machine covering exactly the
constructs the five articles happen to use. Anything else is silently dropped or
mis-nested: a nested list flattens to one level, a second paragraph in a blockquote
merges into the first, a footnote renders as literal text. Nothing fails loudly.

Two constraints shaped the answer and are easy to forget:

- **GitHub Pages serves files.** A request for a path with no file is an HTTP 404 —
  verified against the live site (`/articles/nonexistent/` → 404, and the repository
  has no `404.html`). "Publish" therefore means the file existed before the request.
  No amount of client-side rendering recovers canonical URLs, og cards, JSON-LD
  `url` or sitemap entries for a path that is not there.
- **`AGENTS.md` says `main` is published and owner-synced.** Any automation has to
  either respect that or say clearly which sentence it rewrites.

## Usage (caller's view)

The author, in `mariobgsp/articles` — and this is the whole protocol:

```bash
$EDITOR seventh-thing.md      # `# title`, `> standfirst`, facts table, `| Order | 7 |`
git add seventh-thing.md images/seventh-*.png
git commit -m "content: seventh-thing"
git push                      # the site follows within the hour, or on dispatch
```

No site checkout, no slug list, no sitemap edit, no og image required.

The maintainer, at a terminal — exactly what CI runs:

```bash
git -C ../articles pull                 # or $ARTICLES_SRC, or --src PATH
python3 tools/build-articles.py         # write every generated file
python3 tools/build-articles.py --check # exit 1 on drift; writes nothing
```

CI (`.github/workflows/articles-sync.yml`) runs those same two commands and adds no
transform of its own. It does one thing a human would otherwise do: when the
articles change, it commits the regenerated bytes to `develop` and then
fast-forwards `main` from `develop`. That is the owner's own sync command run by a
machine, which is why `main` keeps a single meaning — published, served and
syncable — but it also means a fast-forward carries every pending `develop` commit
with it. An article push therefore publishes code that was sitting on `develop`,
exactly as if the owner had run the sync at that moment. See
[Open questions](#open-questions-and-risks) if that is not wanted.

## Shape

### Discovery and order, with no list

```python
discover(src)  -> [Path]        # root-level *.md, minus README.md
ordered(arts, report) -> [Article]  # `Order` ascending, undeclared last by slug
```

The filename *is* the slug, so membership has exactly one source: the checkout. A
`*.md` that is not named in `NON_ARTICLE` is published rather than skipped — silently
skipping a half-written article is how an article disappears — and a file with no
`# title` line fails the run by name.

Reading position lives in the article, not in the site: a `| **Order** | 7 |` row in
its own facts table, which the generated page hides. It is per-article metadata, so
adding an article edits no existing file, and an article that forgot its row is
reported and placed last rather than dropped. Duplicate positions fall back to slug,
so the order is a pure function of the files and `--check` can depend on it.

The alternative — deriving order from content — was rejected because it cannot
express the current order: all five articles were added in a single commit
(`f109d89`) and all five carry the same `Verified` date, so every content-derived
rule reorders the published site.

### The generated surface

| Output | Why it is generated |
| --- | --- |
| `articles/<slug>/index.html` | One page per discovered article. |
| `articles/index.html` | Hub cards, spans and stats follow the count. |
| `index.html` region | Article list, count and the `Updated` date, spliced between exactly one `<!-- article:begin -->` / `<!-- article:end -->` pair. |
| `sitemap.xml` | One `<url>` per article plus the two static routes. |
| `assets/articles/*` | Referenced images, with `og-*.png` deliberately kept. |

Three guarantees are structural rather than hopeful:

- **No og:image can 404.** `og_image()` returns the hand-made card when it exists and
  the site default `assets/og.png` otherwise — both 1200×630, so the emitted
  `og:image:width/height` stays truthful. A brand-new article needs no card.
- **No stale page survives.** Page directories whose article is no longer in the
  checkout are removed, and `--check` reports them as drift.
- **No word is lost silently.** `assert_text_coverage()` compares the words written
  in the Markdown against the words in the rendered HTML on every run, so a construct
  that renders as *something* while losing text fails the build. It catches loss, not
  mis-nesting: a flattened nested list still passes, because its text survives.

The page shell keeps its hand-written prose, and its `/articles/<slug>/` links are
checked against the live set — so a renamed article fails the build instead of 404ing.

Writes are validate-then-atomic: every source is parsed, rendered and checked before
the first byte changes, and each file is written to a temp path and renamed. A bad
checkout or a failed check leaves the tree byte-identical.

### Publishing

`articles-sync` runs hourly (plus `workflow_dispatch`, plus an optional
`repository_dispatch`), regenerates, asserts `--check` as a fixed point, and
commits to `develop` **only** when the bytes moved. It then fast-forwards `main`
from `develop` — never a force, never a branch — and asks Pages to build:

```text
POST /repos/{owner}/{repo}/pages/builds
```

That call is the one non-obvious line. A push made with `GITHUB_TOKEN` does not
trigger other workflow runs and does not reliably trigger the Pages branch build, so
waiting for the push to be noticed would mean a green workflow over a frozen site.
The endpoint is documented as having "the same effect as pushing a commit to your
default branch". It is gated on the push having actually moved `main`.

Because the bot only ever fast-forwards, `main` stays an ancestor-or-equal of
`develop`, the owner's documented `git merge --ff-only develop` remains valid, and
the default-branch copy of the workflow keeps itself current.

## Rendering: the feasibility verdict

**Achievable today, no new dependency.** Everything above, plus: figure captions
attached to the image they follow, pull quotes styled as such, heading anchors and a
generated table of contents, and a copy-link control. The ids already exist; only the
anchor and the TOC are missing.

**Achievable with one pure-Python dependency family.** Totality is the point, not
features. `markdown-it-py` (CommonMark + GFM) parses every input by construction, so
an unknown construct becomes text rather than nothing, and a render dispatch over a
closed node union cannot silently skip a kind. `mdit-py-plugins` adds footnotes,
task lists and heading attributes; `Pygments` adds build-time highlighting. All
build-time only, never shipped to the reader.

| Construct | Cost |
| --- | --- |
| Nested lists, multi-paragraph blockquotes, setext headings, hard breaks | free with the parser; today they flatten or merge |
| Footnotes, task lists, definition lists | `mdit-py-plugins`; a little `article.css` |
| Syntax highlighting | `Pygments`; a highlight theme in `article.css` |
| Per-article social cards | `Pillow` + a bundled font, or keep the generic fallback indefinitely |

**Not achievable on GitHub Pages**, and named here rather than promised: comments
(a third party such as giscus, plus an App install), subscribe/email capture (a
provider and a data processor), member gating or personalisation (needs a server),
server-side image transforms, and Mermaid rendered at runtime (the drawn diagram is
already a PNG; the fenced source stays source).

**Three contracts the swap must honour**, each currently load-bearing and untested:

1. `slugify` must stay byte-compatible. `payment-system.md` links to
   `#what-id-fix-next` twice, and the heading is `## What I'd fix next` — stripping
   the apostrophe is what makes those live links resolve. A parser that emits its own
   ids breaks them silently, and `article_page()` splits sections on
   `<h2 id="…">`, so every section id would also degrade to `part-N`.
2. The figure-caption predicate is *a paragraph whose whole text is one emphasis run*,
   not a standalone `*line*` — around nineteen captions are written as multi-line
   italic paragraphs, and `durable-agents.md` has a non-caption emphasis paragraph
   that must not become one.
3. The swap changes every generated byte, so the one-time `--check` diff is a review
   event, not drift to be waved through.

## Synthesis decision

Three candidate designs were produced in parallel and cross-judged; the base is
**branch deploy preserved, with the bot fast-forwarding `main`**. It won because it is
the only shape where the branch `AGENTS.md` calls published, the branch the owner
syncs, and the branch Pages serves stay the same object, and because the bot's
fast-forward keeps the *default branch's* copy of the workflow current — under the
artifact-deploy alternative, the workflow YAML on `main` would have to be re-synced
by hand after every edit, which is the same drift class this change exists to remove.
One rule bends: "sync `develop` and `main` only when asked" gains a bounded exception,
now written into `AGENTS.md`.

Grafted into it:

- The explicit Pages build request, which replaces the base's unverified assumption
  that a `GITHUB_TOKEN` push redeploys the site.
- `assert_text_coverage()`, from the candidate that proposed a fidelity census. The
  census file itself was dropped: for a single author it is a gate that gets
  rubber-stamped, while the coverage check is mechanical.
- Validate-then-atomic writes.
- The out-of-region home-page fixes (count-free prose, derived `Updated` date, and a
  check on every hand-written article link).
- The `slugify` and caption contracts above.

Deliberately not taken from any candidate: the "no build step" family, which was
killed by the 404 constraint, and per-article generated social cards, which buy
little over the generic fallback until articles are actually shared.

## Tradeoffs accepted

- We accept a bot with write access in exchange for an unattended publish, narrowed to
  a fast-forward from `develop` gated on a green `--check`.
- We accept that `main` now has a second writer, in exchange for keeping one meaning
  of `main` (published, served, syncable) instead of three.
- We accept that an article change also flushes pending `develop` commits to `main`,
  because a fast-forward cannot carry less than everything. The alternative — committing
  generated bytes directly onto `main` — breaks the owner's `--ff-only` sync, which is a
  worse cost than an early publish.
- We accept up to an hour of latency, in exchange for needing no secret in the
  articles repository.
- We accept a visible `| **Order** | N |` row in the five articles as published on
  GitHub, dev.to and Hashnode (the site hides it), in exchange for a reading order
  that is not a central list.
- We accept that the "What the runs printed" block stays hand-written and only
  mentions some articles, in exchange for keeping editorial writing out of Python;
  its links are checked, its prose is not generated.
- We accept that `--check` counts pages (7, not 6) because the sitemap is one of them.

## Alternatives considered

- **Client-side rendering from the articles repo.** Rejected on the 404: a path with
  no file cannot be indexable, shareable or canonical, whatever the browser does.
- **Artifact deploy from `develop`.** Viable, and the fallback if the Pages build
  endpoint is unavailable. Lost because it needs a one-time settings flip that no
  workflow can perform, makes `main` non-serving, and adds a recurring hand-sync of
  the workflow file to the default branch.
- **Bot commits straight to `main`.** Breaks the owner's `--ff-only` sync: once `main`
  holds commits `develop` does not, `git merge --ff-only develop` fails.
- **A committed manifest or submodule pinning the article set.** The hand list, moved
  one file over.
- **Keep the hand-rolled renderer and detect leftovers.** The detector only finds
  constructs someone thought to look for, and the mis-nesting bugs live inside the
  hand-rolled rules.
- **Census gate on first use of each construct.** Dropped as a rubber stamp; the
  coverage check gives the loudness without the upkeep.

## Open questions and risks

- **Should the bot touch `main` at all?** It does today, by fast-forward, so an
  article push also publishes whatever was pending on `develop`. The alternative is
  artifact deploy: Pages source becomes "GitHub Actions", the workflow uploads a
  build of `develop`, and `main` stays entirely the owner's — at the cost of a
  one-time settings flip that no workflow can perform, `main` no longer serving, and
  the default-branch copy of the workflow then needing a manual sync after every
  edit. The generator and the workflow are the same either way; only the last three
  steps change.
- **Is the `Order` row the right place for reading position?** It is invisible on the
  site and visible in the article's own metadata table elsewhere. Deleting the five
  rows is a five-line revert that yields a deterministic alphabetical order — the
  fallback is exercised on every run.
- **`pages: write` is not yet proven sufficient** for `POST /pages/builds` on this
  repository, and `gh` is unauthenticated here so neither that nor branch protection
  on `main` could be checked. The first run settles both: the step fails loudly rather
  than silently, and the mechanical fix is `pages: write` on the job or a PAT.
- **The workflow does nothing until it reaches `main` once**, because `schedule` and
  `repository_dispatch` only run the default branch's copy. After that the
  fast-forward keeps it current.
- **GitHub disables `schedule` after 60 days of repository inactivity.** A quiet
  quarter silently stops the sync; any commit, or one manual run, restores it.
- **The articles repo's README still says "The five"** and still lists its own order.
  Out of scope here, and now the only remaining hand-maintained list.
- **Fidelity is still bounded by the hand-rolled renderer** until the swap lands. A
  nested list is flattened today and the coverage check does not catch that, because
  no text is lost.

## Next implementation step

Replace the renderer with the pipeline sketched above in one change: parse with
`markdown-it-py` into a closed node union, render with an exhaustive dispatch that
raises instead of dropping, wire `slugify` and the caption predicate in as tests
first, add `requirements.txt` with exact pins, and read the resulting `--check` diff
as the one-time review it is.
