Keeping JWTs Out of the Browser: an API Gateway With a Server-Side BFF

The Gateway is a small API-management console: define the upstream APIs you call, allowlist what may reach them, and test them from the UI. The interesting engineering is not the CRUD — it is that the session token never becomes readable by a single line of browser JavaScript.

At a glance

  • What it is — a control plane for outbound HTTP APIs plus a runtime that executes them: each ApiGateway record stores a host, a path, a method, a header allowlist, an optional parameter allowlist and a required-body gate.
  • Who it's for — teams that call many third-party APIs and want one place to see, constrain and test them, without putting a credential in front of the browser.
  • The interesting part — the trust boundary is the Next.js server, not the SPA. Every backend call is a server-side fetch behind an httpOnly cookie, and every upstream call re-enforces the allowlists that are stored in the database.

The problem: two credentials in the wrong places

Most SPA-plus-API projects end up with the same two problems.

1 — The token is readable by any script on the page. Storing a JWT in localStorage means one injected script, one compromised dependency, or one careless dangerouslySetInnerHTML is a full account takeover. The token also becomes part of every XSS payload the app ever has.

2 — Any URL the browser can name, the server will fetch. A gateway that forwards whatever path, header or query it is handed is an open proxy: an attacker can reach hosts you never configured, leak credentials you meant to keep local, or use your service as an SSRF pivot.

This project answers both by construction: the browser holds an opaque cookie it cannot read, and the Go service derives the outbound request from persisted configuration rather than from the incoming request.

Why this stack

LayerChoiceWhy this — and not the obvious alternative
Trust boundaryNext.js App Router server (BFF)The session token has to live somewhere the browser cannot read. A server-rendered BFF is already in the stack for the UI, so the token handler costs no extra service.
Session transporthttpOnly + SameSite=Lax cookieRemoves the token from JavaScript entirely and gets CSRF protection from the cookie policy rather than from a custom scheme. Secure flips on in production.
Backend languageGo with chi and pgxThe forwarding path is I/O-bound and latency-sensitive; a small binary with an explicit router and a real driver beats a framework where the middleware order is implicit.
PersistencePostgreSQL, entity-specific queriesThe records are the configuration, and they need constraints (unique identifier, foreign keys to users). internal/store keeps one file per entity instead of a generic repository.
Route tableDeclarative gwRoutes.tsA /gw/* surface that grows by copy-paste eventually diverges. One table means adding an endpoint is one entry, and the BFF mapping is auditable in a single read.
Styling / runtimeStandard Web APIs (fetch, AbortController)The BFF needs a timeout and a cancellation path, both of which are in the platform.

Component walkthrough

  • frontend/src/app/gw/[...path]/route.ts — the catch-all HTTP adapter. Every browser→backend call enters here.
  • frontend/src/lib/bffGateway.ts — BffGateway, the deep module that owns session lookup, the unauthorized response, the backend fetch, the timeout and the envelope translation. Sanitization is private to it, so no call site can forget it.
  • frontend/src/lib/gwRoutes.ts — the declarative route table that maps /gw/* paths onto backend paths.
  • gateway-go/internal/handler/ — router, HTTP adapters and the auth middleware.
  • gateway-go/internal/service/forward.go — ForwardRequest (path name, query params, headers, body) is the typed seam between the HTTP layer and the forwarder, which keeps the forwarding policy testable without a socket.
  • gateway-go/internal/store/ — one file per entity (api.go, account.go, user.go) over a shared postgres.go connection.
  • gateway-go/internal/api/ — the envelope, the error codes and the mapping from service errors to them.

One browser click, end to end

  1. The page calls a literal /gw/... path — never a user-constructed URL, so no user-controlled value reaches the fetch sink as a parameter.
  2. gwRoutes.ts matches the path and resolves the backend path.
  3. BffGateway reads the gw_session cookie, and if it is missing or invalid returns an envelope error rather than calling the backend.
  4. The backend fetch runs server-side with the JWT in an Authorization header, under a timeout and an AbortController.
  5. gateway-go authenticates the JWT, then the service layer loads the stored ApiGateway record for the identifier.
  6. GatewayForward builds the outbound URL from the stored host and path, filters outbound headers and query parameters down to the stored allowlists, enforces the required-body gate, and calls the upstream.
  7. The upstream response is mapped back into the envelope and returned to the BFF, which maps it once more for the browser.

Architecture decisions worth defending

The browser never holds a credential. Decision: the session is an httpOnly, SameSite=Lax cookie minted and read only by the Next.js server. Cost: every backend interaction costs a server round-trip, and the BFF has to exist as a deployment unit. Benefit: the credential is not reachable from the page, which removes an entire class of vulnerability rather than mitigating it.

Allowlists are enforced twice, from two different sources. The BFF sanitizes what it forwards, and the Go service re-derives the outbound request from the persisted configuration. Cost: a header that is allowed in the config but stripped by the BFF fails confusingly. Benefit: no browser-supplied value is ever trusted, so the gateway cannot be used as an open proxy even if the BFF is bypassed.

The URL is encoded exactly once. Query parsing is deliberately tolerant — ?foo becomes foo="" and duplicate keys are last-wins — and canonical encoding happens in a single place (service.BuildForwardURL). Cost: the tolerant parse is a policy a caller has to know about. Benefit: double-encoding bugs, which are the classic source of "works in the UI, fails for the partner" tickets, cannot happen.

One response envelope for every fault. Decision: code: "00" is success, and every failure maps to a numbered code in one package. Cost: an extra translation step for upstream bodies. Benefit: the UI has exactly one error path to implement, and the codes are stable enough to document for other consumers.

Reuse the platform before adding a dependency. fetch, AbortController and the platform's cookie handling are used rather than an HTTP client or a session library. Cost: a little more code in the BFF. Benefit: the dependency surface that has to be patched stays small — which is the same reason the backend keeps net/http, chi and pgx and stops there.

Running it

# 1 · database
cd project && docker compose up -d postgres
psql "$DATABASE_URL" -f project/pg-init-scripts/gateway.sql

# 2 · everything, including the UI, in containers
docker compose up -d --build          # postgres + gateway-go (8080) + frontend (3000)

# or run the halves natively
cd gateway-go && DATABASE_URL=postgres://microservices:password@localhost:5432/gateway?sslmode=disable go run ./cmd/server
cd frontend   && BACKEND_API_URL=http://localhost:8080 npm run dev

# tests
cd gateway-go && go build ./... && go vet ./... && go test ./...
cd frontend   && npm run lint && npm run typecheck && npm test && npm run build && npm run test:e2e

What I observed

This is the part of the design that is easiest to claim and easiest to check. After logging in, from inside the page:

document.cookie => ""
session cookie  => gw_session httpOnly=true sameSite=Lax
BFF 200 /gw/auth/login
BFF 200 /gw/apis
BFF 200 /gw/stores
BFF 200 /gw/apis/detail/gateway-example-1

The session cookie exists, the backend calls all went through the BFF, and document.cookie is empty: the token is not merely "not used by" the frontend, it is unreadable to it.

A second observation, from the Try-it console. Forwarding to a public upstream failed in my sandbox with:

Get "https://api.thecatapi.com/v1/images/search": tls: failed to verify certificate:
x509: certificate signed by unknown authority

That is an environment fact, not a code fault — the container does not carry the intercepting CA this network uses. It is worth showing anyway, because it demonstrates the desired behaviour under failure: the gateway surfaces the upstream's real error verbatim instead of collapsing it into a generic 500, which is what makes an integration debuggable. What I'd fix next

Ordered by how much each item costs to leave alone:

  • The schema and seed rows are a separate step. The Compose file mounts the init SQL, but a native run needs the psql -f command above before the UI has anything to show. A migration step at boot, or a health readout that says "0 APIs configured", would make a first run self-explaining.
  • test:e2e runs against port 3001 to avoid colliding with a local dev server; worth knowing when a run "hangs" on a busy machine.
  • The security posture depends on deployment, not code. COOKIE_SECURE must be true behind TLS; the shipped Compose file sets it to false for local HTTP, which is correct locally and wrong anywhere else.
  • Forwarding inherits the host's CA trust. As observed above, a container with a slim trust store will reject upstreams that the host accepts.
